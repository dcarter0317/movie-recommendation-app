# 0007. Verify: swipe onboarding and personalized feed

How each acceptance criterion in [index.md](index.md) is checked. Run the Vitest and integration checks first, then the `/check verify` browser pass against `next dev` with a local Supabase stack that has the feature 4 seed catalog loaded. Feature 6 (auth) must be in place for the end to end pass; before it lands, the read and job paths take an injected user id in the integration tests.

| AC | Check | Kind |
|---|---|---|
| **AC-1** | With a seeded user at 4 qualifying positives, a request to `/feed` returns a redirect to `/onboarding`; after a 5th like, a request to `/onboarding` returns a redirect to `/feed`. Confirm the gate query is a `count(*)` on `user_movie_interactions` with predicate `reaction_type = 'like' or rating >= 3.5`, not a read of `taste_profile.based_on_count`. | integration + code review |
| **AC-2** | `getOnboardingDeck()` returns `DECK_BATCH_SIZE` rows, all `tmdb_status = 'active'`, none present in the caller's `user_movie_interactions`. Order matches the Bayesian weighted rating computed independently in the test from `vote_average`, `vote_count`, `WEIGHTED_RATING_PRIOR_M`, `CATALOG_MEAN_RATING_C`. Consecutive rows are not all the same primary genre (spread). A second call after marking `DECK_BATCH_SIZE - DECK_REFETCH_AT` reacted returns the next batch with no repeats. | Vitest (ranking, spread) + integration |
| **AC-3** | Seed a user with a `user_movie_interactions` row for every movie above `DECK_MIN_VOTE_COUNT`; `getOnboardingDeck()` still returns a full batch drawn from the widened pool. Seed reactions for every `active` movie except a handful; the deck returns those few, then an end state. | integration |
| **AC-4** | `recordReaction(movieId, 'like')` twice for the same pair yields one `user_movie_interactions` row with `source = 'swipe'`; the second call returns the same `qualifyingPositives`. An unknown `movieId` returns a `Result` error, no row written. | integration |
| **AC-5** | One successful `recordReaction` sends exactly one `feed/taste.recompute.requested` (assert on the Inngest client send spy). Ten `recordReaction` calls within 4s produce exactly one `feed-recompute-taste` execution for that user under `inngest dev`. Code review confirms the send is in the action body, not inside a `step.run`. | integration + code review |
| **AC-6** | After swiping 5 likes, `feed-recompute-taste` writes `taste_profile` with `based_on_count = 5` (or the count with a non null `movies.embedding`), `embedding_model = EMBEDDING_MODEL_KEY`, `last_computed_at` recent, and `embedding` equal to the L2 normalized mean the test computes from those 5 `movies.embedding` values (cosine similarity to the expected vector `> 0.999`). A user with 5 dislikes and 0 positives gets no `taste_profile.embedding` write. Confirm the function uses `asInngest` / the unpooled client. | integration + code review |
| **AC-7** | For a user with a known taste vector, `getFeed()` returns up to `FEED_SIZE` rows ordered by cosine distance to `taste_profile.embedding`, none of them in the exclusion set (`seen` / `skip` / `dislike` / `dismissed_at not null` / watchlisted). `EXPLAIN` on the candidate query shows an HNSW index scan; the statement issues `SET LOCAL hnsw.ef_search = HNSW_EF_SEARCH`. Add `FEED_CANDIDATE_COUNT` exclusions and confirm the feed still returns `FEED_SIZE` (the over fetch absorbed them). | integration + `EXPLAIN` |
| **AC-8** | With `taste_profile.embedding` null, `getFeed()` returns a full list, every pick `mode = 'fallback'`, ordered by the weighted rating. After `feed-recompute-taste` writes the vector, a fresh `getFeed()` returns `mode = 'personalized'`. Exclude all but 3 `active` movies for a user with a taste vector: the feed returns 3 picks and they are `mode = 'fallback'` (fewer than `FEED_SIZE` survived similarity). | integration |
| **AC-9** | For a user whose likes are all sci fi and thriller, a sci fi pick's `reason` is `"Because you like ..."` naming up to `REASON_MAX_TAGS` shared tags, genres before keywords. A pick sharing no tag with the liked set uses the user's single top tag. A user with no qualifying positives gets `REASON_COLD_TEXT`. The tag frequency map is built from at most `REASON_LIKED_SAMPLE` rows. | Vitest (pure `reason.ts`) |
| **AC-10** | In the browser pass, the swipe that crosses the 5th positive shows the "you are all set" confirmation with a working "See my feed" control that lands on `/feed`. Returning to `/onboarding` redirects to `/feed`. | `/check verify` browser |
| **AC-11** | Deck shows a loading state between batches; feed shows a loading state then either stacked cards or the `EmptyState`. `SwipeCard` arrow keys register reactions and the reduce motion branch renders with no drag transform (reuse spec 0005's coverage). Feed cards are reachable by keyboard and show a focus ring. | `/check verify` browser + Vitest |
| **AC-12** | Code review: neither `getFeed` nor `getOnboardingDeck` carries `'use cache'`; both are called after `connection()` or inside `<Suspense>`; both use the pooled request client. Only `feed-recompute-taste` imports the `asInngest` client. | code review |
| **AC-13** | Set `taste_profile.embedding_model` to a stale string; `getFeed()` still returns similarity ranked picks and the run logs exactly one `warn` carrying `userId`, `profileModel`, `catalogModel`. | integration |

## End to end browser script (`/check verify`)

1. Sign in as a fresh user (feature 6). Land on `/onboarding` (AC-1).
2. Swipe: 3 likes, 1 dislike, 1 skip, then 2 more likes. The deck refetches without a visible gap (AC-2, AC-4, AC-11).
3. On the 5th like, the "you are all set" confirmation appears; click "See my feed" (AC-10).
4. `/feed` shows a loading state, then stacked cards, each with a poster, title, year, and a "Because you like ..." line (AC-9, AC-11). First load may be `mode = 'fallback'`; reload after ~15s and it is `mode = 'personalized'` (AC-8).
5. None of the movies reacted to in step 2 appear in the feed (AC-7).
6. Tab through the feed: each card takes focus with a visible ring (AC-11).
7. With the OS reduce motion setting on, repeat step 2: swipes still register by button and arrow key, no fling animation (AC-11).
